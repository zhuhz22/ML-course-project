## Data

The large data directories (`data/raw/`, `data/clean/`, `data/cache/`) are not
committed; they are regenerated by the download and preprocessing steps below.
Raw Kaggle files are in `data/raw/` (49 files, 865 MB, 2023 weeks 1–18 plus the
mock test set). Consolidated to `data/clean/{input,output}.parquet`:

- 4,880,579 input tracking rows, 562,936 target rows
- 272 games, 14,108 plays, 1,384 players (1,178 ever designated for prediction)
- history median 26 frames @ 10 Hz; horizon median 10 frames (long tail to 94)
- target coverage is exact: every predicted player has an output row for every
  frame `1..H`, with no orphans in either direction

### The one real trap in this dataset

Input `frame_id` is the **absolute play clock** (release ≈ frame 26), while output
`frame_id` **restarts at 1** and counts the horizon. A join on the frame column
alone silently pairs release-frame features with future targets. `src/nfl_data.py`
renames both clocks explicitly and asserts the invariant.

## Split

Train = weeks 1–16, validation = weeks 17–18 (strict temporal split). The mock
test games share no `game_id` with the labelled data, so a week-based split is the
closest analogue to the real test.

## Reproduce, in order

The Kaggle API token is read from the `KAGGLE_KEY` environment variable, so the
download step needs it set (and a Kaggle account with access to the competition):

```bash
export KAGGLE_KEY=<your Kaggle API token>   # from kaggle.com -> Account -> Create New API Token
```

```bash
export https_proxy=192.168.48.27:18000 http_proxy=192.168.48.27:18000  # if needed
python3 dl.py                     # download (if data/raw is empty)
python3 scripts/build_parquet.py  # raw CSV weeks -> parquet      (~90 s)
python3 scripts/build_cache.py    # features + targets per split  (~15 s)
python3 scripts/baseline_cv.py    # Baseline 1 + reference points (~20 s)
python3 scripts/baseline_xgb.py   # Baseline 2, saves models      (~10 min)
python3 scripts/ablation_xgb.py   # 6 feature-group ablations     (~15 min)
python3 scripts/seed_variation.py # 3-seed stability              (~15 min)
python3 scripts/error_analysis.py # role / horizon / speed / direction breakdown
python3 scripts/predict_test.py   # mock-test submissions, validates gate format
python3 scripts/make_figs.py      # report figures
python3 scripts/make_report.py    # reports/midterm_report.pdf
```

Everything is CPU-only; XGBoost here has no CUDA build and none is needed.

## Feature-group ablations (Baseline 2)

| Variant | feats | RMSE | Δ |
|---|---|---|---|
| full model | 127 | 0.750 | — |
| no interaction features | 73 | 0.764 | +0.014 |
| short (5-frame) history only | 97 | 0.772 | +0.022 |
| no history summaries | 103 | 0.773 | +0.023 |
| neither history nor interaction | 49 | 0.787 | +0.037 |
| no landing-point geometry | 114 | 1.000 | +0.250 |

The supplied landing point dominates; interaction features help modestly; long
motion history is largely redundant beyond a short window.
